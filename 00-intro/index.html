OpenGL 是什么

这一节不开窗口、不画图，只建立四个后面每节课都要用到的概念：CPU 和 GPU 怎么分工、OpenGL 到底是什么、什么叫状态机、什么叫对象。

下面这条命令跑的是本节的源码，它不开窗口，只在终端把课程目录打印一遍——打印出来的这份目录就是后面每节课的索引：

$ racket 00-intro/intro.rkt

0.1 CPU 与 GPU 的分工

你写的 Racket 代码跑在 CPU 上。CPU 的核心不多（家用机一般几个到几十个），每一个都很快，强在判断、跳转、调度——也就是决定「接下来该做什么」这类串行的活。这一帧画什么、用哪个着色器、传什么参数，都是 CPU 定下来的。

显卡上的 GPU 正相反：它有成千上万个很小的核心，单个并不快，但能同时对一大批数据做同样的运算。它不擅长复杂的控制流，擅长的是「把同一段运算套到一百万个顶点、一百万个像素上」。

所以图形程序的分工是固定的：CPU 决定画什么，GPU 负责把每个顶点、每个像素都算一遍。OpenGL 就是 CPU 向 GPU 下命令的那条通道——它自己不计算图形，只负责把「要画什么」传下去。

0.2 OpenGL 是规范，不是库

OpenGL 不是一份可以下载安装的库，它是一份规范（specification）：规定有哪些函数、叫什么名字、参数是什么、调用之后必须产生什么结果。

真正干活的是显卡驱动里的实现。同一份代码在你的机器上跑的是 NVIDIA / AMD / Intel 驱动里的那套实现，换台机器就是另一套——只要两边都照规范做，程序就不用改。也正因为如此，「我这儿能跑」和「别人的机器上也能跑」是两件事。

Racket 这边用到的名字来自 opengl 包，它是规范里那些 C 函数的绑定：gl-clear 对应 C 的 glClear，gl-viewport 对应 glViewport。racket-shader 提供 #lang glsl 这套 DSL（用 S 表达式写 GLSL），racket-shader-opengl 再把它和 opengl 绑在一起，负责编译、链接和类型大小计算，让你不必手写着色器字符串。

0.3 状态机：先设状态，再发命令

OpenGL 内部记着一大堆状态：清屏色是什么、当前绑着哪块缓冲、当前用哪个着色器程序……每条命令作用的对象都是「当前状态」，参数里通常不带目标。

最典型的一对是 gl-clear-color 和 gl-clear：前者只是「记住」一个颜色，什么都不画；后者才真的按记住的颜色把缓冲擦掉。顺序反了就白设。下面这两行摘自第 1 课的绘制代码：

01-window/window.rkt（on-paint 里）源码 ↗
         (gl-clear-color (* 0.5 (+ 1.0 (sin t)))
                         (* 0.5 (+ 1.0 (sin (+ t 2.0))))
                         (* 0.5 (+ 1.0 (sin (+ t 4.0))))
                         1.0)
         (gl-clear gl-color-buffer-bit)

关键点以后所有「先 bind 再操作」的写法都源于此：想往哪块缓冲传数据，先 gl-bind-buffer 把它绑成当前缓冲；想用哪个着色器程序，先 program-use。命令本身不带目标，目标来自当前状态。

0.4 对象与 id

GPU 上的资源——缓冲、着色器程序、纹理——统称对象（object）。CPU 这边拿不到对象本身，只拿到一个整数 id：buffer-new（底层是 gl-gen-buffers）生成 id 交给你，此后所有涉及这块缓冲的命令都用这个整数去指它。

要记住 id 只是名字，本身不含数据。真正的数据在显存里，得用 buffer-upload（底层是 gl-buffer-data）这类命令从 CPU 侧的内存拷过去。所以「缓冲」这个词有时指显存里那块存储、有时指那个整数，读文档时看上下文。

0.5 渲染管线主线

后面几节课讲的其实就是下面这条主线上的每一格：

CPU 把顶点数据准备好交给 GPU，GPU 按顺序跑过这些阶段，最后落在屏幕的像素上。中间三个固定阶段各干一件事：图元装配把顶点拼成三角形，光栅化把三角形变成一堆像素，再由片元着色器决定每个像素什么颜色。第 2 课起，我们讲的就是怎么把数据喂进这条管线、以及怎么写那两个方括号里的程序。

关键点方括号里那两段（图 0-1 标蓝的）是你写的程序，叫 shader，用 GLSL 写。但可编程阶段不止这两段：几何着色器、曲面细分控制/求值、compute 也都是你写的程序。本教程的主线只用顶点+片元两段，其余阶段（IA、图元装配/裁剪、光栅化、逐片元操作）才是 GPU 的固定行为，只能设参数、不能改代码。

图 0-1 为了好记只画了两段可编程。完整顺序和各自的可编程与否是这样：

顶点数据 → [顶点着色器] → [曲面细分控制] → [曲面细分求值] → [几何着色器]
        → 图元装配 / 裁剪 / 剔除 → 光栅化 → [片元着色器] → 逐片元操作（ROP） → 屏幕
旁路：[compute shader]（不在图形管线上，自己读写缓冲/纹理）
阶段可编程版本门槛本教程
顶点着色器是2.0+主线，第 2 课起
曲面细分控制 / 求值是4.0+330 core 下不可用
几何着色器是3.2+可用，本教程未展开
图元装配 / 裁剪 / 剔除否—固定功能，只能设状态

为什么本教程只写两段顶点+片元两段已经能画出后面所有章节的东西；几何着色器适合做爆炸、法线可视化这类「一个图元变多个」，曲面细分适合高细节曲面，compute 适合与绘制无关的通用并行计算——都不是入门必需，读完主线再按需补即可。

0.6 core profile 与 version 330 core

早期 OpenGL（2.x 及以前）有一整套「立即模式」：用 glBegin / glEnd 把顶点一句一句喂进去，管线大部分是固定的，你能插手的只有开关和几个固定函数。

现代 OpenGL 只留可编程管线，那套旧接口在 core profile 里已经被删掉了。开 core profile 就是在说「我只用现代管线」。

这件事在代码里有两端：Racket 那边是 (send cfg set-legacy? #f)（不启用旧式固定管线），GLSL 那边是每个 shader 的第一行 (version 330 core)。两边说的是同一件事，必须对上。第 1 课开窗口时会写 set-legacy? #f，第 2 课每个 shader 的第一行会写 (version 330 core)。

坑两端不匹配会直接失败：还开着 legacy 却写 (version 330 core)，或者在 330 core 下用旧版语法，都会在创建上下文或编译 shader 时报错，而报错信息通常不会直说「版本不对」。遇到莫名其妙的着色器错误时，先回来检查这两行。

0.7 计算放在哪：GPU 不是唯一选择

前面说「CPU 决定画什么，GPU 负责算」，这句话容易让人误以为「图形计算只能在 GPU 上做」。不是的。矩阵乘法、光照公式、纹理采样，本质上都是普通的数学运算；同一套公式既可以在 CPU 上算，也可以在 GPU 上算，区别只是「在哪里算、算完怎么送到下一步」。

OpenGL API 自己并不计算图形。它主要做三件事：

  1. 传数据：把顶点、索引、纹理、uniform 从 CPU 内存送到 GPU。
  2. 设状态：告诉 GPU 接下来用哪个 program、哪个 VAO、开不开深度测试。
  3. 启动计算：gl-draw-* 让 GPU 跑顶点/片元着色器。

真正「算」的是你写的 shader，或者 CPU 侧的 Racket 代码。同一件事通常有两种做法：

任务CPU 做法GPU 做法本教程为什么选 GPU
顶点变换 CPU 先算好每个顶点的世界/裁剪坐标，再上传结果 上传原始顶点 + 矩阵，顶点着色器逐个乘 顶点多、相机每帧变；GPU 并行且不用回传中间结果
光照 CPU 逐顶点算颜色，或离线烘焙成顶点色/lightmap 片元着色器逐像素算 diffuse/specular 像素数远大于顶点数，逐像素质量更好
纹理采样 CPU 自己按 UV 取像素，再写进顶点色/新纹理 纹理单元按 UV 采样 硬件过滤/mipmap，且采样发生在每个片元
模型解析 CPU 读 OBJ/glTF、拼顶点/索引 GPU 不适合做文件 I/O 和串行解析 这是 CPU 的活；解析完再上传
文字 CPU 用字体引擎把字画成 bitmap 把 bitmap 当纹理，画 2D/3D quad 混合：CPU 生成字形，GPU 贴到几何上

所以「用 OpenGL」不等于「所有计算都在 GPU」。更准确的说法是：把适合并行、数据量大的计算搬到 GPU；把串行、一次性、文件 I/O 和复杂控制流留在 CPU。判断标准可以先用这三条：

  • 同一段公式要对成千上万个顶点/像素重复吗？→ 优先 GPU。
  • 结果每帧都要回读到 CPU 吗？→ 回读通常很贵，尽量留在 GPU。
  • 是一次性的准备/解析/小规模计算吗？→ CPU 更简单。

后面怎么读正式章节会随着用例讲 API；复习章节会把「API 调用」和「它触发的计算」重新对一遍，并给出 CPU 版和 GPU 版的同一公式。你会发现：API 的数量其实不多，真正变化的是计算放在哪、数据怎么流动。

0.8 GPU 硬件与数据模型（加深）

0.1 和 0.7 只讲了“CPU 决定、GPU 并行”和“计算放在哪”。这一节再往下走一层：GPU 里大致有哪些硬件单元、OpenGL 的数据模型是什么、以及每个常用 GL 调用到底在 GPU 上留下什么。不同厂商的 GPU 细节不同，下面是现代桌面 GPU 的典型结构。

0.8.1 GPU 不是“很多 CPU 核”

CPUGPU
核心少量、复杂、强单线程大量、简单、强吞吐
擅长分支、跳转、串行、低延迟同一段代码套到大量数据上
执行模型乱序、预测、深缓存SIMT：一组线程锁步执行同一条指令
弱点并行度有限分支发散、串行、复杂控制流

GPU 用大量线程来隐藏内存延迟：一个线程等显存时，调度器切到另一个线程。它不追求“单线程很快”，而是追求“很多线程同时推进”。

0.8.2 统一着色器核心与 SIMT

现代 GPU 的顶点、几何、片元、compute shader 通常跑在同一批统一着色器核心上，只是调度阶段不同。线程按 warp / wavefront 分组（常见 32 或 64 个），同一组执行同一条指令；遇到分支时，不同分支会分时执行，这叫发散。

这解释了两件事：

  • 片元 shader 里写“每个像素走不同分支”的代价可能很高；能写成无分支/统一控制流就尽量写。
  • 寄存器、shared memory 用量会影响同时驻留的 warp 数（occupancy）；occupancy 太低，内存延迟藏不住。

顶点 shader 每个顶点执行一次；片元 shader 每个被三角形覆盖的片元执行一次；compute shader 按 workgroup 执行。它们不是“CPU 函数”，而是被 GPU 调度器批量调用的程序。

0.8.3 固定功能单元

除了可编程核心，GPU 还有一批固定功能单元：

单元作用
命令前端 / 调度器接收驱动提交的命令，分发给各单元
Input Assembler（IA）按 VAO 描述从 VBO/EBO 取顶点和索引
图元装配 / 裁剪拼三角形、做视锥裁剪、背面剔除
光栅化器把三角形变成片元，插值 varying
纹理单元（TMU）按 UV 做寻址、过滤、mipmap、纹理缓存
ROP深度/模板测试、混合、写 framebuffer

注意这张表只列固定功能单元，不是说表外都不可编程：顶点、几何、曲面细分控制/求值、片元、compute 都是可编程阶段，完整清单和版本门槛见 0.5 的补注。本教程只用顶点+片元两段；IA、光栅化、ROP 这些是固定的，只能设状态（gl-enable、gl-blend-func、gl-viewport 等）。

0.8.4 内存层次与带宽

寄存器（每线程） → shared / L1（每计算单元） → L2（全 GPU） → 显存 VRAM → PCIe → 系统内存 CPU

越往左越快、越小；越往右越慢、越大。CPU 和 GPU 之间隔着 PCIe，带宽通常远低于显存带宽，所以：

  • 顶点、纹理、索引尽量只上传一次，之后留在显存。
  • 每帧只传变化的小数据：矩阵、光源参数、少量 uniform。
  • 避免 GPU → CPU 回读（`gl-read-pixels` / `gl-finish` 会等待 GPU，打断流水线）。
  • 大量小 draw call 的 CPU 提交开销和状态切换也可能成为瓶颈，和显存带宽是两回事。

0.8.5 OpenGL 数据模型

OpenGL 用“对象 + 绑定点 + 状态机”描述 GPU 资源。名字（GLuint）只是句柄，背后是驱动管理的内存/状态。

对象数据模型谁使用
Buffer（VBO/EBO/UBO/SSBO）线性字节块IA / shader / uniform 系统
Texture图像 + 采样参数 + mip 链TMU / 片元 shader
Shader / Program编译后的 GPU 代码 + uniform 存储调度器 / shader 核心
VAO顶点属性格式 + buffer 绑定IA
Framebuffer颜色/深度/模板附件ROP

shader 的输入也分得很清楚：

  • attribute：每顶点一份，从 VBO 经 IA 取。
  • uniform：一次 draw 内共享，来自 program 的 uniform 存储/常量缓存。
  • texture / sampler：TMU 资源+采样状态。
  • varying：顶点 → 片元的插值数据，存在片上，不落显存。

GL 调用大多是“把命令放进队列”，CPU 不一定等 GPU 做完。只有回读、gl-finish、查询结果等操作才会强制同步。

谁负责释放这张表里的名字只是句柄：gl-gen-* / build-program 分配的对象归调用方，用完要 gl-delete-*。它们的内存在驱动里，不在 Racket 堆上，GC 看不见也不会回收（为什么不能用终结器，见 racket-shader-opengl 的 DESIGN.md §3.1）。而 vec-array 这类 Racket 值不用你管——上传是复制，复制完那份内存就交给 GC 了。两者分界见 02 · 2.9。

0.8.6 每个常用 GL 调用在 GPU 上做什么

调用GPU/驱动侧的实际作用
gl-gen-buffers分配名字/句柄；通常还不分配显存
gl-bind-buffer改上下文/VAO 的绑定状态；不拷贝数据
gl-buffer-data分配 buffer 存储，把 CPU 字节经驱动/ DMA 拷进去；可能因 buffer 正在使用而等待

gl-tex-image-2d分配纹理存储，拷贝像素，可能做格式转换/行对齐

gl-delete-*标记删除；GPU 可能等资源不再使用后才真正释放

0.8.7 一次 draw 的完整生命周期

CPU: 设状态（program / VAO / texture / uniform）
  → 提交 draw 命令
GPU 前端: 取命令
  → IA: 按 VAO 从 VBO/EBO 取索引和顶点
  → 顶点 shader: 每个顶点一次，输出 clip 坐标 + varying
  → 图元装配 / 裁剪 / 剔除
  → 光栅化: 三角形 → 片元，插值 varying
  → 片元 shader: 每个片元一次，采样纹理/算光照
  → ROP: 深度/模板测试、混合、写 framebuffer
  → 屏幕

CPU 通常在这条流水线还没跑完时就已经返回、继续提交下一帧命令。只有你显式同步或回读，才会等 GPU。

0.8.8 对写代码的意义

  • 少改状态：相同 program/VAO/纹理的物体尽量放一起画。
  • 少回读：GPU → CPU 很贵；需要的结果尽量留在 GPU。
  • 数据常驻：静态 VBO/纹理只传一次；每帧只传小 uniform。
  • 减少 overdraw：不透明物体从前到后画，透明物体从后到前。
  • 避免 shader 发散：片元里少写“每个像素走不同分支”的重逻辑。
  • 先测量再优化：瓶颈可能在 CPU 提交、带宽、填充率或 shader 计算，不一定在同一处。

一句话GL 调用绝大多数只是“改状态 / 搬数据 / 排队”；真正让 GPU 大规模并行计算的是 draw call 触发的顶点/片元 shader。理解硬件单元和数据模型，才知道每个调用在 GPU 上留下了什么、以及为什么这样组织代码。

小结

概念 一句话
CPU 与 GPU CPU 串行、负责判断和调度，决定画什么；GPU 用成千上万个小核心并行算每个顶点和像素
规范与实现 OpenGL 是一份文档，规定函数名和行为；显卡驱动里的那份实现才是真正干活的代码
状态机 先设状态再发命令，命令作用在「当前状态」上，所以到处是「先 bind 再操作」
对象与 id GPU 上的资源叫对象，CPU 侧只有它的整数 id；数据在显存里，不在 id 里
管线主线 顶点数据 → [顶点着色器] → 图元装配 → 光栅化 → [片元着色器] → 屏幕
core profile 只用现代可编程管线；(send cfg set-legacy? #f) 和 (version 330 core) 是同一件事的两端
